RxBridge — Architecture & Sequence Diagrams

Reference sheet for interview prep. Right-click any diagram → "Save image as" (or select and copy) to lift it out individually.

1. Five-stage patient visit pipeline

Why this flow

  • Each stage exists to remove one specific piece of manual work from the consultation: Intake replaces the doctor asking "what brings you in" from scratch, Documents replaces manually reading old prescriptions, Memory replaces flipping through a patient's paper history, Context replaces the doctor doing that synthesis mentally under time pressure, and Summary replaces the patient trying to remember what was said.
  • The order is deliberate: intake and documents both feed memory before context is generated, because a pre-consultation brief is only useful if it already reflects the full picture — generating context before memory is populated would just produce a shorter, less useful note.
  • Summary is last on purpose — it only fires after the doctor has actually recorded an outcome, so the patient receives what really happened in the visit, not a prediction of it.

2. Layered system architecture

Why this flow

  • The layers are separated by rate of change and responsibility, not just for tidiness: channels change fastest (a new messaging channel is just a new adapter), infra changes slowest (Firestore schema, GCP services). Keeping them in separate layers means a channel change never touches an agent, and an agent change never touches infra.
  • Agent orchestration sits in its own layer because it's the only layer that needs to reason and make decisions — everything above it is transport, everything below it is storage. That separation is what makes it possible to swap an LLM provider or add a seventh agent without touching the channels or the infra.
  • Retrieval sits between orchestration and infra deliberately: agents never query Firestore or the vector store directly — they go through the retrieval layer, so the hybrid-RAG logic (deciding what's structured vs. semantic) lives in one place instead of being duplicated inside every agent.

3. High-level visit sequence

sequenceDiagram
  participant CA as Clinic assistant
  participant IN as Intake agent
  participant DOC as Document agent
  participant MEM as Memory agent
  participant CTX as Context agent
  participant DR as Doctor
  participant COM as Comms agent
  participant PT as Patient

  CA->>IN: Free-text intake
  CA->>DOC: Upload prescriptions/notes
  DOC->>MEM: Structured extraction
  IN->>MEM: Structured intake data
  MEM->>CTX: Longitudinal history
  CTX->>DR: Pre-consultation brief
  DR->>CTX: Consultation outcome
  CTX->>COM: Visit summary
  COM->>PT: WhatsApp/email summary
  PT-->>COM: Feedback (optional)

Why this flow

  • Intake and document upload happen independently from the same clinic-assistant interaction, because a patient may bring old prescriptions without needing to say much verbally, or vice versa. Both paths converge on Memory — it's the single place where free-text and document data get reconciled into one patient record, rather than two competing sources of truth reaching the doctor separately.
  • Context generation only happens after memory is updated, and the doctor's outcome flows back into context before the summary goes out — that return arrow is what makes this human-in-the-loop rather than fully automated: the system proposes context, the doctor decides, and only the decided outcome gets communicated to the patient.
  • Feedback is a dashed, one-way return at the end, not a blocking step — the patient's visit is considered complete once the summary is sent; feedback is a signal for improving the system later, not a gate on anything.

4. Intake agent — low-level sequence

sequenceDiagram
  participant CA as Clinic assistant app
  participant GW as FastAPI gateway
  participant ORC as LangGraph orchestrator
  participant INA as IntakeAgent
  participant LLM as LLM router
  participant VEC as Vector store
  participant FS as Firestore
  participant PS as Pub/Sub

  CA->>GW: POST /api/v1/intake with patient_id, free_text
  GW->>GW: auth_middleware() then validate_payload()
  GW->>ORC: graph.invoke(state IntakeState)
  ORC->>INA: IntakeAgent.process(state)
  Note over INA: guardrail_check(): PII redaction, prompt-injection filter
  INA->>LLM: llm_router.generate(prompt, model=cost_tier)
  Note over LLM: cost-aware routing: Gemini Flash for extraction, Claude for synthesis
  LLM-->>INA: structured_symptoms.json
  INA->>VEC: embed_and_upsert(vector, patient_id)
  INA->>FS: write patients intake record with idempotency_key
  FS-->>INA: ack
  INA-->>ORC: return updated_state
  ORC->>PS: publish intake.completed event
  Note over ORC,PS: Eventarc decouples stages, document agent triggers async
  GW-->>CA: 202 Accepted with trace_id

Why this flow — and where the structured data actually goes

  • Auth and validation happen at the gateway, before the graph is invoked — so IntakeAgent only ever runs on requests that are already known to be legitimate and well-formed. This keeps the agent's own logic focused purely on clinical extraction, not security.
  • Guardrails run before the LLM call, not after — PII redaction and prompt-injection filtering happen on the raw input first. This matters because once text reaches a third-party LLM API, you can't take it back; filtering has to happen on the way in, not as a check on the way out.
  • How the structured data is stored: once the LLM returns structured_symptoms.json, it's written to Firestore under a path like patients/{id}/intake/{visit_id} — a structured, queryable record, not a blob of text. The same payload is also embedded and pushed into the vector store via embed_and_upsert(), so the same fact exists in two forms: exact-match structured fields (for things like "list every symptom logged for this patient") and a semantic embedding (for things like "find visits where the patient described something similar to today's complaint").
  • Why both a structured write and a vector write: this is what lets the memory agent later do hybrid retrieval — pull hard facts straight from Firestore, and pull semantically related history from the vector store — instead of relying on vector search alone, which is weaker at exact recall of structured facts like dates or medication names.
  • The idempotency key on the Firestore write protects against the same intake being recorded twice if the clinic assistant's app retries a slow request — without it, a flaky network could double-count symptoms in the patient's history.
  • The handoff out is a publish, not a direct call — ORC publishes intake.completed to Pub/Sub and returns immediately. The memory agent doesn't get triggered here; it's the document agent's completion (or a timeout) that eventually causes memory to pick up both intake and document data together, which is what the next diagram shows.

5. Document agent — low-level sequence

sequenceDiagram
  participant CA as Clinic assistant app
  participant GW as FastAPI gateway
  participant ORC as LangGraph orchestrator
  participant DOC as DocumentAgent
  participant OCR as Vision/OCR model
  participant LLM as LLM router
  participant FS as Firestore
  participant PS as Pub/Sub

  CA->>GW: POST /api/v1/documents upload file
  GW->>GW: validate_file_type() then virus_scan()
  GW->>ORC: graph.invoke(state DocumentState)
  ORC->>DOC: DocumentAgent.process(state)
  DOC->>OCR: extract_text(image, model=med_gemma)
  OCR-->>DOC: raw_text plus confidence_score
  Note over DOC: if confidence_score below threshold, route to human_review_queue()
  DOC->>LLM: llm_router.generate(prompt=structure_extraction)
  LLM-->>DOC: structured_medications.json
  DOC->>FS: write patients documents record
  FS-->>DOC: ack
  DOC-->>ORC: return updated_state
  ORC->>PS: publish document.completed event
  GW-->>CA: 202 Accepted with trace_id

Why this flow

  • OCR/vision extraction and structuring are two separate model calls, not one — the OCR model's only job is turning an image into raw text with a confidence score; a separate LLM call then structures that text into typed fields (medication name, dosage, date). Splitting them means a low-confidence OCR result can be caught and handled before a downstream model confidently hallucinates structure on top of garbage text.
  • The confidence-threshold branch is the most important design decision here: if OCR confidence is below threshold — which happens often with handwriting — the record goes to a human_review_queue() instead of silently entering the patient's structured history. This is the concrete answer to "how do you avoid a misread medication ending up in a patient's record": low-confidence data never reaches memory unreviewed.
  • The write to Firestore mirrors the intake agent's pattern — same patients/{id}/... structure, same idempotency approach — so the memory agent can query documents and intake data with one consistent access pattern instead of two different schemas.
  • File validation and a virus scan happen at the gateway, before any model ever sees the upload — a clinic assistant's device is an uncontrolled entry point, so the file is treated as untrusted until it clears both checks.

6. Memory & context agent — low-level sequence

sequenceDiagram
  participant PS as Pub/Sub
  participant ORC as LangGraph orchestrator
  participant MEM as MemoryAgent
  participant FS as Firestore
  participant VEC as Vector store
  participant CTX as ContextAgent
  participant LLM as LLM router
  participant DR as Doctor app

  PS->>ORC: event intake.completed and document.completed
  ORC->>MEM: MemoryAgent.process(state)
  MEM->>FS: query_structured_history(patient_id)
  FS-->>MEM: patient_records list
  MEM->>VEC: similarity_search(patient_embedding, k=10)
  VEC-->>MEM: relevant_note_chunks
  Note over MEM: merge_structured_and_unstructured() hybrid RAG fusion
  MEM-->>ORC: return longitudinal_history
  ORC->>CTX: ContextAgent.process(state)
  CTX->>LLM: llm_router.generate(prompt=context_synthesis, model=high_tier)
  LLM-->>CTX: pre_consultation_brief
  CTX->>FS: write patients context record
  CTX-->>ORC: return updated_state
  ORC-->>DR: notify_doctor(brief_ready)

Why this flow — how structured intake data is actually used here

  • The memory agent wakes up on both events, not either one alone — it waits for intake.completed and document.completed (or a timeout if one is missing) so it never generates a partial picture from only half the visit's data.
  • Two separate reads, then a merge: query_structured_history() pulls the exact structured records that the intake and document agents wrote earlier — symptoms, medications, dates — straight from Firestore. Separately, similarity_search() queries the vector store for semantically related notes from past visits, using the patient's embedding as the query. Neither read alone is enough: the structured read gives you hard facts but misses nuance in free text from prior visits; the vector read gives you semantic recall but is unreliable for exact facts like "which medication, which dose."
  • merge_structured_and_unstructured() is the actual hybrid-RAG step — this is the function to describe in detail if asked "how does your RAG work": it's not one retrieval call, it's two retrieval calls over two different stores, reconciled into a single longitudinal history object before anything gets sent to an LLM.
  • Context generation uses a stronger, higher-cost model (model=high_tier) than the earlier extraction steps — this is the cost-aware routing decision in practice: cheap models are fine for pulling structured fields out of text, but synthesizing a doctor-facing brief from years of history is the one step where model quality actually changes the output's usefulness, so it gets the better model.
  • The brief is written to Firestore before the doctor is notified, so it exists as a durable, timestamped record — if a doctor is interrupted mid-review or asks "what did the system tell me last time," the exact brief they saw can be retrieved rather than regenerated (which could produce a slightly different answer).

7. Comms & feedback agent — low-level sequence

sequenceDiagram
  participant DR as Doctor app
  participant ORC as LangGraph orchestrator
  participant COM as CommsAgent
  participant LLM as LLM router
  participant WA as WhatsApp API
  participant EM as Email service
  participant FS as Firestore
  participant PT as Patient
  participant FB as FeedbackAgent

  DR->>ORC: submit consultation_outcome
  ORC->>COM: CommsAgent.process(state)
  COM->>LLM: llm_router.generate(prompt=plain_language_summary)
  LLM-->>COM: patient_summary_text
  COM->>COM: render_template(summary, language=patient_lang)
  COM->>WA: send_message(patient_phone, formatted_message)
  Note over COM,EM: email is fallback if WhatsApp delivery fails
  COM->>EM: send(patient_email, formatted_message)
  COM->>FS: write patients summary_sent record
  COM-->>ORC: return updated_state
  PT-->>FB: feedback_webhook(rating, comment)
  FB->>FS: write patients feedback record
  FB->>ORC: publish feedback.received event

Why this flow

  • This stage only starts once the doctor submits an outcome — the comms agent never sends a summary based on the pre-consultation brief alone, because that brief is a prediction, not a record of what was actually discussed or decided. This is the second half of the human-in-the-loop story: the doctor's input is the trigger, not just an input.
  • render_template() runs before sending — the plain-language summary is localized to the patient's preferred language at this step, since the doctor-facing brief and the patient-facing summary are different documents generated for different audiences from the same underlying visit data.
  • WhatsApp is primary, email is an explicit fallback — reflecting that in the clinics this is built for, WhatsApp delivery is far more reliable for reaching patients than email, but email exists as a safety net so a summary is never silently lost if a WhatsApp send fails.
  • Feedback comes back through a separate webhook, to a separate agent, published as its own event — deliberately decoupled from the comms agent's send path, so a slow or missing feedback response can never delay or block the visit being marked complete. It's a signal channel, not a dependency.
