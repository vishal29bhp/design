Why this flow

  • One door for every tool call. Agents never connect to tools directly. Routing all traffic through a single enforcement point is what makes the controls universal: a new agent or a new tool inherits identity checks, policy, credential brokering, limits and audit without any extra integration work.
  • Cheapest rejection first. Identity is checked before policy, and policy before any credential is touched. A caller that cannot prove who it is, or a request the policy denies, is stopped before it costs a vault lease or reaches a downstream system.
  • Credentials are released last. The vault prepares a short-lived, scoped credential, but the gateway only attaches it at dispatch, after the rate limiter and guardrails pass. In the rate-limit simulation the prepared credential is discarded and never reaches the CRM.
  • Denials are as visible as approvals. The blue audit lines leave every stage, not just the tool. A blocked attempt is often the most important event for a security team, so it is recorded with the same identity, policy version and trace ID as a successful call.

2. Three decision paths: allowed, blocked, throttled

Why three paths, one record

  • Green, red and blue mean the same thing everywhere. Green is traffic that passed every check, red is traffic the gateway stopped, and blue is evidence. The same colors are used in the brief's Mermaid flow, so leadership and client reviewers read both documents the same way.
  • Blocked requests fail closed and early. A denied request never gets a credential and never reaches the tool, so a prompt-injected or misconfigured agent cannot "try its luck" against a downstream system.
  • Throttling protects the tool, not just the budget. A runaway loop is stopped at the gateway with a clear 429 and retry time, so the downstream CRM or database never absorbs the burst, and the operations team is alerted from the audit stream.

3. Control plane and data plane

Why separate the planes

  • The data plane decides; the control plane defines. The gateway evaluates every request in milliseconds against configuration it already holds. Identities, policies, secrets and approval rules are managed separately, so a policy change is a reviewed commit, not a gateway redeployment.
  • Policy as code makes governance reviewable. Access rules live in a versioned repository with peer review and history. Every audit record names the policy version that made the decision, which is exactly what an auditor asks for.
  • Humans stay in the loop where it matters. High-impact operations, such as bulk exports, deletions or payments, pause in the data plane until a named approver responds through the approval workflow, and that decision joins the same audit trail.
  • Evidence leaves through one exit. The audit log is append-only and exports to the client's existing security monitoring and GRC tools, so the gateway adds evidence to their program instead of creating a new silo.
